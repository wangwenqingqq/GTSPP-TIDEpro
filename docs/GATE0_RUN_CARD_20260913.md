# Gate 0：六次自然发布的累积维护控制

登记于 2026-09-13，GPU 测量前。状态：实现及正确性门禁准备中。

## 本轮边界

只启动第一阶段的有界诊断，不等同于完成 7–14 天计划。用已有 SureChEMBL
256-bit 指纹，沿 2026-06-01、06-15、07-01、07-17、08-04、08-18、08-25
顺序累计。使用 `splitmix64(stable_id XOR 20260913) % 38 == 0` 对初始库和
每个真实增量一致抽样，约百万行。称为“真实历史的一致抽样回放”，不是全库、
不是生产稳态、不是 64 次自然发布。只读原文件；所有输出写入新项目目录。

旧 transition audit 报告六次均为 insert-only；本轮重新校验抽样 ID 唯一性、
实际 popcount、每次行数平衡及所有查询的完整 CPU 结果。全源文件 SHA256
和抽样文件 SHA256 均记入输入清单；不把旧审计当成本轮重新审计了所有原分子。

## 冻结比较合同

- 四个普通策略：`all_delta` 不合并；`periodic2` 每两次发布合并所有 runs；
  `size_tiered` 按时间相邻、从最新端开始，当前一个 run 的行数不超过最新 run
  的两倍时合并，重复至条件不满足；`compact` 每次发布完全压实。
  这些是预设控制，不是已经在开发 trace 上调优完成的最强基线。
- 同一份历史 `exact_runs_kernel<4>`、CTA=256、整数谓词、popcount 区间、
  单次融合发射、持久 workspace、同步完成/排序/完整 ID+intersection+union。
  保留历史源 SHA，并验证 kernel 字节未改。只改维护及测量 harness。
- Q=1，阈值 7/10 与 4/5；固定 32 个非空查询：16 个初始库查询，
  每次后续发布各 2 个、最后一次额外 4 个。选择规则固定为抽样文件中的
  均匀间隔行。查询来源不是独立外部分布；未来查询在进入之前可无命中。
- 每个请求获取并持有一个 epoch 到完整输出结束；本轮单线程顺序回放，
  无并发写入，因此不能证明 GPU in-flight 并发回收安全或维护干扰。
- 每请求容量 65,536 hits，溢出显式失败并停止，不截断；空数据库指纹允许，
  空查询拒绝；每个 stable ID 只允许一次插入；相同指纹不同 ID 保留。
- tracked device allocation 上限 256 MiB，包括数据、旧版本持有数据和 runtime
  缓冲；另外记录 cudaMemGetInfo 的观察值。预计预算不绑定，不能声称测了
  接近满显存。每策略独立重建/释放，禁止把其他策略副本算进当前预算。
- compaction 用 host popcount 分桶的线性复制，再上传新 GPU run；登记 CPU
  构建、上传、物理复制字节和 old/new 共存峰值。这不是最优 GPU merge，
  维护时间不能用来声称新策略算法优势，也不与查询时间机械相加模拟并发。

## 正确性先于计时

先对同一抽样历史再按 cohort 均匀取至 4096 base / 每 delta 至多 64 行，
构成有明确标签的小 correctness fixture，不混入性能表：每个 epoch、策略、查询、阈值都与不剪枝
CPU 全扫描逐条比较，检查旧 epoch 在发布后仍保持完整结果，运行 memcheck
和 synccheck；失败则不计时。随后约百万行完整 CPU oracle 预计算一次，
每次 GPU 测量逐条比较完整输出；oracle 与比较时间单列，不混入服务时钟。

计时前另用 65,537 个相同指纹、不同 ID 的合成记录验证容量 65,536 的
显式 overflow，以及空候选区间。该合成 guard 只用于正确性，绝不进入性能表。

服务时钟包括 bounds、descriptor、enqueue、count/payload D2H、排序/hash；
不包括输入准备、驻留、oracle、结果文件写入。维护测量包括 host 构建及新 run
上传，发布只是 GPU 上传完成后指针替换；冷启动单列。每 epoch/阈值 8 次
warmup，记录但不纳入 32 次测量。四个新进程用四种策略的循环顺序轮换。
保留全部尝试和污染标记，不自动替换慢样本。统计以进程为重复单位，报告
每进程结果和配对查询比，不把同一进程的 32 个查询冒充 32 次独立部署。

## 资源与停止条件

pro6000-8 仅使用物理 GPU 1（UUID 以启动时核验为准），不动 GPU 0/2 的
现有任务、不改时钟/功率、不启端口。全程持有既有 TIDE global lock 和
GPU 1 lock，启动前查询空闲状态，运行中检查外来占用，只停止自己的子进程。
每次进程最多 15 分钟，首轮总 GPU 命令最多 30 分钟，CPU 准备最多 10 分钟。

本轮只能回答有限历史、小规模、Q=1、非并发下普通布局成本是否不同。
若差距小/不稳定，不虚构新机制；若差距可重复，先查扫描行数、尾块、
descriptor、输出和 CPU 排序开销。下一步才扩至 10M/Q=8/64 和 shadow/
实际发布两组并发实验。既不预设 3×，也不把此轮无显著差异当作等价证明。

## 首次 GPU 执行前的资源修订

原 GPU 1 在准备期间已被其他任务占用，第一 wrapper 又在锁打开阶段失败，
无 GPU 子进程启动。2026-09-13 复查 GPU 0–5 均忙、GPU 6/7 空闲；改用
物理 GPU 6 / `GPU-865ae1f0-780e-d04c-5ec3-4deccea65f82`（启动前再次验证）。
锁仍使用既有 TIDE global lock，加与实际 GPU 对应的单卡锁；不替换锁 inode。
设备函数、输入、策略、输出、重复次数和计时范围不变，不混用其他 GPU 旧结果。
