# Gate 0：百万行累积维护控制的第一份结果

**结论：本轮未观察到完全压实的稳定查询收益，先不引入新维护机制。**
这不是“所有普通策略等价”的证明，也不是对大规模、并发、预算受限维护的反证。
本轮完成了可复用实验路径和正确性门禁；Pro 提出的核心系统问题仍未闭合。

**2026-09-13 后续计时勘误：** Gate 1 审查发现，本轮 wrapper 每请求重建
`OwnedHostDB::view()` 的 cumulative metadata，需要 O(N) CPU 扫描，而这段
工作位于旧 `service_ms` 计时之外。因此下文旧 service 表不是 acquire epoch
到完整结果返回的端到端延迟；原始数值保持不改，但不得用它们与 Gate 1
计算加速比。修订口径见 [Gate 1 合同](GATE1_CONTRACT_20260913.md)。

## 正确性结果

- 原始 24 项 CPU 测试重跑通过，增加 7 项，本环境合计 **31 项通过**。
- CPU 不剪枝、直接对 fingerprint AND/OR 计数，生成 fixture 和百万行
  各 448 个完整结果向量；不复用 GPU 的 popcount 区间或存储 popcount 算式。
- **7,168 个计时请求**、1,792 个 warmup 请求都逐条匹配完整 CPU 向量。
  四策略在相同 epoch/query/threshold 下候选数、ID/交并计数和输出均一致。
- fixture/两次 sanitizer 合计 5,376 个请求全部匹配；memcheck 和 synccheck
  各报告 `0 errors`。这不包含专门 leak-check、racecheck 或并发回收压力测试。
- 更新后的旧 epoch 完整检查：计时进程 192 次，fixture 进程 144 次通过。
  这是顺序执行中保留旧 owner，不是 GPU in-flight 并发读写证明。
- 合成 guard 请求 65,537 个 hits，超过容量 65,536 时明确 overflow，
  不返回截断向量；空候选区间检查通过。合成数据未进入性能表。

## 查询结果：没有稳定方向

以下每个策略先在各进程内对同 epoch/query 的服务延迟比做几何均值，
再以 **4 个进程**为重复单位计算 log-t 95% 区间（df=3）。包含六个更新后
epoch；初始 epoch 不计入主比较。每个 epoch 等权，不模拟真实发布间隔。
比值为“该策略 / 每次完全压实”，大于 1 才表示完全压实更快。

| 策略 | 阈值 0.7 延迟比 [95% CI] | 阈值 0.8 延迟比 [95% CI] |
| --- | --- | --- |
| 不合并 | 0.999 [0.940, 1.062] | 0.991 [0.934, 1.052] |
| 每两次发布合并 | 0.990 [0.901, 1.088] | 0.993 [0.910, 1.083] |
| 大小分层合并 | 0.982 [0.902, 1.068] | 0.983 [0.910, 1.063] |

全部区间跨 1，不能声称已证明等价。仅看最后 epoch 也没有改变判断。
逐进程比值、kernel 时间比和 final-epoch 结果全部保留在
[summary.json](../results/gate0_20260913/summary.json)，不挑掉慢进程。

| 策略 | 最终 runs | 查询中位数 µs | 六次发布准备累计 ms，四进程范围 | tracked device 峰值 MiB |
| --- | ---: | ---: | ---: | ---: |
| 不合并 | 7 | 39.57 | 1.12–2.00 | 44.38 |
| 每两次发布合并 | 1 | 39.06 | 110.23–134.28 | 87.76 |
| 大小分层合并 | 4 | 39.09 | 3.12–4.91 | 47.45 |

## 能解释什么，不能解释什么

相同输入的精确候选行数完全相同，平均约 280,521 行/请求。平均尾部空线程
从不合并的 589 降到完全压实的 125；按总工作量汇总，差额约为候选行数的
0.165%。descriptor 平均从约 155 bytes 减至 40 bytes。它们确实变少，
但本次未形成稳定的服务延迟改善。扫描字节是代码层逻辑计数，不是 NCU
测得的 HBM 流量；尚不能把波动归因到某一个 CPU/GPU 阶段。

256 MiB 是 **data + query workspace 的显式分配额度**，不含 CUDA context/
driver 的隐式内存。观察到的整卡已用值峰值约 669.9 MiB，高于这个额度；
不能称作“总 VRAM 被严格限制在 256 MiB”。本轮只证明 tracked 数据/缓冲
未触及额度，尚未闭合 Pro 要求的全口径固定显存实验。

同样，`old_epoch_logical_bytes` 包含与新 epoch 共享的 runs，不等于独占的
未回收字节。报告保留这个字段名和边界，不把它当作新增版本内存压力。

## 决策与下一轮

**暂缓：** 当前证据不支持引入“查询感知整理控制器”、新维护单位或新布局。
不恢复旧 GTS++ direct-insert/γ>1 精确性主张，不把本结果包装成新算法。

**继续补测，但先修实验能力：**

1. 将版本共享/独占内存、old-reader 释放、完整维护生命周期计时分开，建立
   包含 context/workspace/旧版本的全口径预算门禁。加故障注入与真正 in-flight
   reader 测试，不能用这次顺序 owner 检查替代。
2. 固定共同的批量执行层，扩到约 10M、Q=8/64；不能把 Q 次同步单查询称为
   native batch。普通策略参数只在独立开发 trace 上选择，保留 test trace。
3. 分别运行固定已发布集合的 shadow 维护和实际增长发布，记录队列、上传/
   构建、版本持有、足够暴露请求；不人为 sleep 延长上传冒充实际干扰。
4. 自然版本只有六次转移，仍是有限历史；如需逼近容量，另列有明示构造规则
   的 controlled stress，不把它叫作自然稳态。

本轮的结果是“门禁跑通、当前小规模差异未成立、关键边界已列出”，不是
7–14 天研究计划已经结束。原始观测和失败尝试不删除。
